## Implementation boundary

`am3d/ai/providers.py` defines one host-selected `Provider` protocol with
adapter-family identities for fake, Agent CLI, local OpenAI-compatible, and
remote API providers. Only the fake is implemented. A request contains the
fixed prompt, user brief, response schema, deadline, and canonical response
byte ceiling; it has no executable, arguments, output root, active document,
project path, or credentials. Results carry raw bounded bytes, host/provider
identity, status, optional transport fields, typed failures, nullable usage,
and nullable latency.

`am3d/ai/provider_contracts.py` parses a versioned strict envelope containing
`schema_version`, `intent`, `assumptions`, `approximations`,
`required_components`, and `recipe`. It composes the existing generated
provider recipe schema rather than implementing another recipe policy. The
parser bounds provider bytes at 1 MiB before decoding, limits JSON nesting to
64, rejects duplicate keys, invalid UTF-8, non-finite values, unknown or
missing fields, and schema violations. Provider-facing texture paths are
excluded by the generated recipe schema.

`am3d/ai/prompt.py` builds a deterministic stable contract prefix with two
examples and puts the bounded brief last. Briefs are limited to 4,096
characters / 16 KiB UTF-8; the whole prompt is limited to 64 KiB. It includes
no repository, document, filesystem, or credential context.

`am3d/ai/orchestrator.py` makes exactly one provider call. After response
parsing, it invokes the existing `authorize_recipe(response.recipe,
host_selected_preflight_root)` before calling `GenerationRunner.start(response.recipe)`.
The M2 runner repeats policy validation using its private output root and owns
worker execution, deterministic checks, cancellation, and publication. No
provider fields configure either call. Provider, parser, or policy failures
launch no worker; there is no fallback, retry, or repair loop.

The fake supports valid output, malformed JSON, duplicate keys, invalid UTF-8,
oversize, transport failure, nonzero exit, timeout/hang simulation, invalid
recipe, policy/path rejection, AI resource-limit rejection, texture-path
attempts, command/output-root field attempts, quota/rate-limit, authentication,
refusal, unavailable provider, and unsupported adapter. Known fake usage is
preserved; unknown token counters and latency remain null.

## Security checkpoint answers

1. Can provider output select an executable? **No.** Adapter selection belongs
   to the host; provider output is parsed as JSON data.
2. Can it select command-line arguments? **No.** Requests have no command or
   argument fields, and unknown response fields fail.
3. Can it select an output root? **No.** The root comes from the host-owned M2
   store and is not part of the provider response contract.
4. Can it cause arbitrary filesystem reads? **No.** The provider request has
   no document or filesystem data; provider recipe fields cannot name texture
   input files.
5. Can it cause arbitrary filesystem writes? **No.** Only validated recipe
   exports can reach the M2 runner, whose AI policy confines output paths to
   its host-owned private root.
6. Can it reach credentials? **No.** No credential abstraction or credential
   value is passed to providers, and no real adapter exists in M3.1.
7. Can it bypass `authorize_recipe(...)`? **No.** Preflight calls the existing
   policy before runner start.
8. Can it bypass the M2 worker? **No.** Valid recipes are passed to the
   existing `GenerationRunner`; provider code cannot invoke the worker.
9. Can oversized/malformed content consume unbounded memory? **No.** The
   parser accepts at most 1 MiB and JSON nesting is bounded. Future stream
   adapters are required to stop at limit plus one byte and enforce the
   request deadline.
10. Can failure fall back to another provider? **No.** There is one selected
    provider call and no retry or fallback path.
11. Can unknown usage become zero? **No.** Unknown counters and latency are
    nullable and remain null.
12. Can provider content become shell, Python, or import code? **No.** The
    output contract only yields recipe-v1 data, then existing host policy and
    the fixed worker decide execution.

## Deferred and preserved scope

- Agent CLI, local HTTP, and remote API adapters are deliberately unimplemented;
  no CLI flags were guessed, no credentials were added, and the optional API
  remains inert/off.
- Automatic validation/execution repairs, retries, provider fallback, usage
  accounting persistence/UI, and provider/model bake-off are not implemented.
- M2 worker, policy, checks, cancellation, stale-result protection, and
  publication code were not changed. `am3d.spec` only bundles the model-facing
  recipe schema and discovers the new orchestration module.
- No M4 or M5 features were added. Manual/offline recipe and CLI workflows
  remain available.
- Remaining non-blocking plan items are later-phase work: exact real CLI
  contract verification, subscription/API accounting, local endpoint support,
  repair-loop design, and measured provider/model selection.

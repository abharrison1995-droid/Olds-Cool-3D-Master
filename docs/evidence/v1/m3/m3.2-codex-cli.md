- Static comparison showed the production M3.1 schema was incompatible with the documented strict Structured Outputs subset: it had `oneOf`, optional properties, dynamic object maps, `const`, and string length keywords. Strict mode requires every property and `additionalProperties: false`; the docs support `anyOf` and definitions. This makes schema-dialect incompatibility the best-supported explanation for the two earlier failures, but the unretained messages prevent claiming their exact original error. See [OpenAI's Structured Outputs schema subset](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas).
- Added `codex_output_schema.py`, a deterministic Codex-only projection from the accepted M3.1 schema. It converts the current disjoint `oneOf` branches to `anyOf`, `const` to equivalent `enum`, string length limits to regex constraints, requires all declared fields, and closes dynamic maps. It intentionally narrows the provider's expressible recipes; M3.1's response parser, AI policy, and M2 runner remain unchanged and authoritative. Tests show a valid projected response passes the canonical parser, while texture, authority fields, and open parameter-map values are excluded.

Read/write/project/repository sentinel hashes were unchanged, and no sentinel marker appeared in the structured response or local diagnostic.
